# 系统凭据存储迁移设计

状态：已按本设计实施，并通过 Windows 凭据库实机往返与自动化测试。应用首次读取每个账号时执行迁移；测试使用虚构凭据，未主动读取或修改用户的真实账号文件。macOS/Linux 仍待对应平台实机验证。

## 当前数据面

`AppConfig` 在账号 JSON 中包含 Canvas Token、jAccount Cookie、视频 Cookie、签到密码、LLM API Key 列表、OAuth Consumer Key 和 JBox Access Token。`App::save_config` 序列化整个配置；日志脱敏只保护诊断输出，不加密账号 JSON。`get_raw_config` 及设置页的原始配置预览也会受到迁移影响。应用数据的“备份”当前复制版本化数据存储，并非完整账号配置/系统凭据备份。

## 目标契约

1. 账号 JSON 只保存普通设置、凭据后端标记与稳定引用 ID。秘密字段写入当前 OS 用户的 Windows Credential Manager、macOS Keychain 或 Linux Secret Service。跨平台 Rust `keyring` 4.2 的 `v1` 模式提供相应后端，但实际依赖/特性和 Linux 无图形会话的行为须锁定并分别测试；见 [官方 crate 文档](https://docs.rs/crate/keyring/4.2.0)。
2. 每个账号和 Canvas 实例使用独立条目；引用 ID 根据稳定账号标识派生，不能包含 Token 或 Cookie。写入后读回校验，再替换磁盘配置。任何写入/校验失败时原配置保持可读，界面显示失败原因，禁止静默退回明文。
3. 启动时找不到密钥环或密钥条目时，非秘密设置仍可加载，秘密值视为未登录；禁止把空值保存回密钥环引用。提供“重试读取”和“重新登录”路径。
4. 现有账号逐个迁移，记录格式版本。迁移要幂等；中途中断后重新启动可判断旧明文、新引用或双写过渡状态。旧配置文件被完整替换前，不能删除唯一可用凭据。
5. 备份明确区分“应用数据”和“凭据”。普通备份不携带秘密，跨设备恢复后须重新登录；如果将来支持凭据导出，另行设计加密导出与用户密码，不把明文放进 ZIP、诊断报告或 CLI 输出。

## 验收矩阵

- Mock keyring 注入：写失败、读回不符、条目丢失、重复迁移、中断恢复、多账号/多实例隔离、账号删除与回滚。
- Windows Credential Manager 实机：首次迁移、重启、改密、切号、备份恢复、卸载后的行为；测试不使用真实个人凭据。
- macOS Keychain 与 Linux Secret Service 实机或隔离 CI：同等场景；Linux 无图形/无 DBus 场景应显示不可用，不静默写明文。
- 检查账号 JSON、原始配置预览、MCP/CLI、诊断日志及备份均不包含迁移后的秘密。

## 实施说明

`src-tauri/src/app/credentials.rs` 把 Token、Cookie、签到密码、LLM API Key、OAuth Key、JBox Access Token 和可能带签名 URL 的课程作业绑定文件按账号与 Canvas 实例写入系统凭据库。较长的凭据 JSON 按 UTF-8 边界拆成不超过 1800 字节的条目，以适配 Windows 凭据大小限制。每次保存使用新的引用版本：所有条目写入并读回校验后，才以同目录临时文件原子替换账号 JSON；失败时旧文件不变。替换后尽力删除旧条目。首次读取旧文件时按相同步骤迁移；切换到其他账号时才迁移该账号。读取失败时只加载非秘密设置；凭据库暂时不可用时仅提示重试，确认条目缺失或引用不匹配时才提供清除引用并重新登录。清除引用不会删除系统中的旧条目。

账号 JSON 中增加 `credential_version`、`credential_ref`、`credential_chunks`。设置页“配置预览”只显示去除秘密字段后的结构。应用数据备份不包含系统凭据，跨设备恢复需重新登录。便携模式仍使用当前系统用户凭据库，移动目录后需重新登录。旧版明文文件被替换后，文件系统历史版本或外部备份不会自动清除；用户应自行管理这些备份。

本轮未在 macOS/Linux 实机验证凭据库；这些平台仍使用同一 `keyring` 原生后端，凭据库不可用时不回退到明文写入。Windows 的虚构凭据往返测试单独执行并清理条目。
